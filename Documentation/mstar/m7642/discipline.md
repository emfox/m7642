## 1 判读纪律：什么才算读数

**只有整屏纯色算数。**

- 不许叠加图案，不许拿颜色序列当读数。**看最后停在那一屏。**
- 判据是"整屏纯色"，条纹 / 花屏 / 渐变一律不算。
- **土黄不能判 rung**：`0xCCCC` 是我们自己 stub 的填充色，内核一被跳转执行第一眼必然土黄。
  且 `0xcccc` 与 `0xCCCCCCCC` 在 RGB565 下同色，无法区分。
- **洋红来源不明**：曾经以为 mboot 进 recovery 会画洋红底 `boot_recovery.jpg`，但 2026-11-20
  实测 `find / -xdev -iname "*boot_recovery*"` 零命中、`/tclconfig` 下只有 5 个品牌 `boot0.jpg`
  ⟹ 该图**不存在**，那句 `run_command("bootlogo … boot_recovery.jpg")` 必然失败。
  所以停在洋红**既不能判"内核没跑"，也不能判"跑到第几级"**。见 [display.md](display.md) §九。
- `0x4210` 是**暗紫蓝 RGB(66,65,132)**，不是中性灰。真灰是 `0x4208` / `0x8410`。
- 哨兵色必须避开 `0xCCCC` / 白 / 红 / 绿 / 黄 / `0x4210` / `0x8410`。

**为什么定这么死**：`ladder4/6/8` 的 rung 与 beacon 四版**逐字节相同**，结果却一次纯绿、三次花屏。
代码相同而结果不同 ⟹ 拿颜色序列当读数等于自欺。

**反汇编核对镜像，不要信"当前源码"。**

- `head.S` 源码里的检查点顺序与 `.img` 里的实际排布**不一致**。
- raw binary 上 `--start-address` 无效：必须先按偏移切段，再
  `objdump -D -b binary -m aarch64 --adjust-vma=<vma>`。
- `code1` 在 Image **偏移 4**，算跳转目标时 **PC = base + 4**。按 `base+0` 算会差 4 字节，
  会误判成"镜像坏了"。

**向人询问观测结果时，选项必须互斥、完整。**

- **必须单列"全黑 / 全白 / 无信号"**。漏掉这个基本情况，对方只能挑一个近似项，
  记录下来的却是另一件事。
- **不能把两种状态塞进同一个选项**。犯过：`"纯色洋红 + 条纹，无图案"` 自相矛盾，
  对方选了，我按"纯色"推出一整套判读（2026-11-20）。
- **不能把"没变化"和"没看清"合并**。又犯过：实际是"一片黑"，被记成"涂色无效"，
  进而推出"fb0 不是扫描源"这个错误结论（2026-11-20）。
- 观测项超过三个时，**逐项单独问**，不要一次给一屏选项。

**为什么定这么死**：这两次都不是看错屏幕，而是**问错问题**。选项设计本身就成为污染源，
下游所有推论都建在错误记录上，且很难自查——因为"记录"看起来是对方亲口确认的。

**先划清判据的盲区，再拿它推结论。**

- 这台机器 **adb 走 WiFi** ⟹ 「adb 有反应」只等于「Android 完整起来了」。探针挂住 /
  内核只跑到 recovery / 落回待机，在 remote 侧**完全同形**。
- ⟹ 凡是要区分「没起来」的原因，必须另有**不依赖 Android** 的读数（人眼看屏、或下一次启动读）。
- 代价：2026-11-21 用「有没有 adb / 多久回来」连推三轮，得出「探针没返回」「镜像没被执行」
  两个错误结论，最后靠零改动镜像对照才推翻。

**跨轮对比之前，先列出「除目标变量外还有哪些不同」。列不出来就写"不可比"。**

本项目的易变项（每一轮实验都可能不同，必须逐项核对）：

| 项 | 举例 |
|---|---|
| ladder blob | 窗口 disable、cache clean、色值、`HALT` 开关、blob 长度 |
| env | `recoverycmd` 是否带 `mmc erase.p misc`、`MstarUpgrade_complete`、`WDT_ENABLE` |
| 刷入位置 | recovery 槽 / boot 槽、BCB、misc 是否被擦过 |
| 镜像内容 | 哪个内核、哪版 head.S |
| 判读手段 | 颜色 / 点密度 / 文字 |

- 犯过（2026-11-20）：拿 4.19 的表现去解释"为什么和 7.3 不同"，而两次之间至少四个变量不同
  ——ladder 版本、`recoverycmd` 是否擦 misc、色值、`HALT`；且两次"表现"都不是实测，
  都来自覆盖率只有 0.01% 的颜色通道。
- **"以前是 X，现在是 Y ⟹ 说明 Z" 这个句式，必须先证明 X 和 Y 是在相同条件下测得的。**
  做不到就写"**不可比**"，绝不要写"不同"。

## 2 赌注纪律：刷机之前先算成本

**`boot` 和 `recovery` 都是单向车道。**

- 刷坏 `boot`：logo → 几十秒 → 待机，**按电源键只是重播同一段**，adb 永远不回来。
  唯一出路是 U 盘救砖（mboot 无失败回退）。
- **`recovery` 槽不是"零成本场地"**：mboot 对 `boot-recovery` 是**非消费式**的，写进 `misc` 之后
  每次开机都进 recovery。已经踩过一次锁死。
- ⟹ **跑非厂值内核挂了就没 adb；「挂了就 `adb reboot`」是自相矛盾的，不许再写这句话。**
- ⟹ **不要反复"按一下看看"。** 「回待机」= PM51 直接切电 = **硬断电**，`/data` 会损坏，
  坏了之后更难救，形成自我强化。
- ⟹ **不要用 `sysrq` 制造软复位。** `echo b > /proc/sysrq-trigger` 走 `machine_restart`，
  不 umount、不等写缓存落盘，对 `/data` 与「回待机」同等有害（2026-11-20 实测：一次就把设备
  送回「logo → 3 秒 → 回待机」）。`panic=0` 又堵死了 `echo c`：它只挂死、不重启。
  要软复位只有两条路——让被测内核自己崩（WDT），或接受 `adb reboot` 的硬断电。
  - **2026-11-21 10:18 又犯了一次（血账）**：为了验 pstore/pmsg 通道，跑了
    `sync; echo c > /proc/sysrq-trigger`。结果 `getprop ro.boot.bootreason` = **`kernel_panic,sysrq`**
    ⟹ 实际路径是 panic → `panic=0` 不重启 → 挂住 → **`wdt_enable 10` 把设备硬复位**，
    等于又给 `/data` 补了一次非正常断电。这次侥幸没坏（`/sys/fs/ext4/mmcblk0p26/` 的
    `errors_count=0`、`first/last_error_time=0`，`/data` ext4 正常挂载 6%），但**结论不变：
    不许再用 sysrq**。
  - 顺带纠正一条事实：`/proc/sys/kernel/sysrq` 实测是 **0**，可 `echo c > /proc/sysrq-trigger`
    照样生效 —— 往 `/proc/sysrq-trigger` 写是独立入口，不受 `sysrq` 开关约束。
    「sysrq=0 所以 echo c 没用」这个旧结论是错的。

**换场地 / 换方案之前，先用零改动的东西把「场地」本身判掉。**

- 2026-11-21：在 recovery 槽连赌四轮，最后靠**厂值镜像原样**（`6272b10d…`）放进去 90 s
  起不来 Android，才判定是场地不行、不是探针不行。这一步本该第一个做。
- ⟹ 顺序固定：**场地能不能出读数 → 工具能不能出读数 → 才开始赌自研代码**。

**断言 env 要按字段，不能按整块 md5。**

`MstarUpgrade_complete` 是一次性标志（mboot 读到 `1` 就消费掉、写回 `0`）⟹ 整块 env 的 md5
每次上电都会变。2026-11-21 用整块 md5 做写前断言，白烧一轮。

**刷机前必须核对的三件事**

1. `/system/etc/install-recovery.sh` 是 `.disabled`（否则每次 Android 启动都会用
   `/system/etc/recovery.img` 把槽整段覆盖）。
2. `/data/local/tmp/rec.head.bin` 的 md5 是厂值（见 confirmed-facts §D）。若不是 ⟹ 厂值回滚已失效。
3. `misc` 的 BCB 不是 `boot-recovery`。

**MMU 开着的时候，只能做「要测的那一次访存」，答案先放寄存器，关了 MMU 再落盘。**

代价：2026-11-22 追 `br x8` 时连挂两发、白费两次物理断电。第一发是探针 blob 盖掉了
`Image+0x36c0c0` 的 code1 shim（280 B 放在 `+0x36c000`）；第二发是 MMU 开着就往
`0x23090000` 写记录——stash 页不在 idmap 里，那一写本身就把机器挂死了，
于是「挂了」既不能证明 VA 不可读，也不能证明任何事。正确写法：`mrs/msr sctlr_el1`
把 M/C/I 关掉之后再写 stash（正常 tramp 一直是这么做的）。
**推论：任何 "NO_RETURN" 必须先排除「探针自己写错了」再当结论用。**

**构建目录的移动/清理必须做「重建 + md5 对账」。**

代价：2026-11-22 清理 `~/kbuild` 时，一条 glob 映射写反（`add "out/$c"` 把源写成裸文件名），
phase A 把 `m7642-out/` 整个删空——5.1 GB、175 张历史镜像没了重建脚本之外的副本。
补救办法正是纪律本身：源码在、工具链在，跑一遍 `build-*.sh` 再逐张比文档里的 md5，
27 张全部一致，等于没有损失。**推论：上机镜像永远是"可重建产物"，不是资产**；
真正要保住的是源码、脚本、md5 记录，以及 `backups/` 里的救砖包。

**设计新探针之前，先 grep `probes/` 和 `confirmed-facts.md`。**

代价：2026-11-22 花掉三次断电去验「7.3 是不是被 fault 打死的」——而 2026-11-21
§27 已经用自建向量表实测证明**零异常、是空转**，§28 连最强候选（`wfe` 等从核 /
dtb `cpu-release-addr` 不匹配）都写好了。代码没丢，丢的是**结论没进交接单**：
`HANDOFF.md` 与 `NEXT-SESSION.md` 里当时既没有"空转"也没有 `wfe`。现在两块顶部都加了
「当前最强结论」块。**新会话开工第一件事是读它，而不是从"卡在哪一级"重新出发。**

**晚期检查点（`start_kernel` 之后）带 `wdt_enable 60`；红外只对"待机"有效。**

红外 POWER 在 AP 活着时由软件处理（厂商 PM 驱动的状态机 `gRTPM_Live`），AP 一挂就没人
做那一步；只有 MCU 处于唤醒键模式（待机/关机）时它才自己断电重启。所以"红外救不回"
不等于硬件坏了。可行做法：`wdt_enable 60` 让设备自己复位回待机，再红外一次
（10 s 的狗不行——交接链要 30–35 s，§34.4）。

**挂死后自动救回已经脚本化，不需要人拔插。**

`tools/host/tv-wait.sh`：先等，等不到就**发红外电源键**（`tvpower.sh on`）再等，并在
输出里标明"这一次挂过"。所有 runner（`run-postmmu`/`run-cmd17`/`run-wt`/`run-wr1`/
`run-clk`/`run-hangtest`）都已接上 ⟹ 一发的成本从"等人拔插"降到"多等 25 秒"。
实测：待机态按电源键 → adb 可用 25 s。

**别用短超时 WDT 兜底跑探针：它会把"能回"变成"挂死"。****WDT 自动复位已被否证（三条路径），不要再试。**

11-21 实测：mboot `wdt_enable 10/120`、厂 `HAL_WDT_Start`（空桩）、`MDrv_WDT_*`、直接写寄存器
——**都不咬**。此前几次"自己回来"是 BCB 没写、走了 `bootcmd`，与狗无关（标记法证明）。
唯一会 warm reset 的是 **panic**（厂内核 `[WdtHeartBeatTas]` 喂的 5 s 狗，panic 停掉所有 CPU
后没人喂）——但 7.3 探针里没有这个条件。
**推论：不存在"挂了还能自动回来 + 记录还在"的路径；只能靠"只打会返回的检查点"。**



代价：2026-11-22 12:00 布防 `wdt_enable 10` 之后，**每一发都挂**，我据此怀疑了四五个
探针、花了四五次断电，最后用"同一张 `f6dd1e79` 镜像 + 只改 env"才钉死因果：交接链
（拷 19.7 MB 厂内核 + 厂内核起到喂狗）要 30–35 秒，狗 10 秒就咬。
**判据：任何"突然全都不回来"的现象，先怀疑环境（env/镜像/工具链），再怀疑探针。**

**DDR stash 只在同一次启动内有效；跨复位要用 eMMC。**

代价：2026-11-22 花了三次拔插 + 两次红外才弄明白。`0x23080000`/`0x23090000` 落在
mboot 每次启动 `mmc read.p dtb 0x100000` 覆盖的 `0x23000000–0x230FFFFF` 里，
而待机态还会切断 DDR 电源。所以"探针写了记录"与"复位后还能读到"是两件不同的事，
不要混。另外 `adb reboot` 是硬断电 ⟹ 设备停在待机，得按电源键（`tools/host/tvpower.sh on`
可脚本化，不需要人）。

**删任何东西之前，先确认它不在"救砖路径"上。**

同一天的清单里差点有 `backup/fix/rescue-fast.bin`（47 MB，**唯一能修 boot 的包**，
`tools/host/boottest.sh` 的默认值）。判据不是"名字像不像历史产物"，而是**谁在引用它**：
`git grep` 一遍仓库里的路径引用，比看文件名可靠。

**跳厂内核之前必须把 `x0..x5` 还给 mboot 的值（尤其 `x2`）。**

代价：2026-11-22 09:0x，code1 的 eMMC 探针改用 C 之后连续挂死 6 次。根因：C 按 ABI 可以
随意用 `x0..x18`，而厂内核入口会把 **`w2`** 存进 `boot_args[2]`；纯汇编桩恰好没碰。
判据是「凡是 C 路径就挂、凡是汇编就过」。规则：任何要跳厂内核的桩，入口保存
`x0..x5`、交接前恢复（`x3/x4` 清 0、`sp` 回 0）。

**「进了 recovery」只能用 misc 标记证明，`ro.boot.bootreason` 不算。**

代价：2026-11-22 08:03 的一发 ctl 报「Android 起来了」，stash 却是 dtb 残渣——事后查是
`adb reboot recovery` 没生效（走了 `bootcmd`），而 `ro.boot.bootreason` 仍显示 `recovery`
（reason 串会被下一次启动继承）。标记法：往 misc **末尾**写 4 KB `0xA5`，
`recoverycmd` 的第一条 `mmc erase.p misc` 会擦掉它；标记消失才算真进了 recovery。

**任何「到达」必须由 stash 证明，不能只看「设备回来了」。** 2026-11-21 20:1x：
多数 rung 判定只等了 `sys.boot_completed=1` 就宣布"到了"。但若 `adb reboot recovery` 没生效、
mboot 走了 `bootcmd` 直接进 Android，设备同样会"回来"，于是给出**假阳性**——这能一次解释
`0x465E80` 一会儿"过"一会儿"不过"的全部矛盾。
规则：`到达` 必须验证 stash 的 `magic == "M764"` **且** `x30 == image_base + off + 4`；
不满足就记 `INCONCLUSIVE`，不参与二分。

**「没回来」这种判定：先算清等待预算，再用插座恢复，不要靠无限延长等待。**（2026-11-25 修订）

旧的"等 ≥ 300 s"规则来自没有智能插座的年代：靠红外碰运气、且不确定电视是否已经被打开，
只能用长等待去躲"慢启动"。现在开机/恢复是受控序列（`tools/host/socket.sh recover`：
OFF → 10 s → ON → 3 s → IR POWER），预算按实测：

- 交接链（拷 19.7 MB 厂内核 + 厂内核起到喂狗）**30–35 s**；
- Android 到 `sys.boot_completed` 再 **~25 s**；
- ⟹ **等 120 s** 足够；没起来就插座恢复并判 ❌，不要长等、不要反复按电源键。

- 记录到达时的 uptime；
- 关键结论重复 2 次一致；
- **"到达"必须由 stash 的 `magic == "M764"` 且 `x30 == site+4` 证明**，"设备回来了"不算
  （插座恢复、正常开机都会让设备回来）。

**探针里任何「长时间」常量，先算一遍量级再上机。**

- 2026-11-21 15:2x：`paint-hold.S` 想空转约 10 s，写成 `movk x9, #0x2, lsl #48`（应为 `lsl #32`），
  实际 1.4×10^14 次迭代 ⟹ 等于死循环 ⟹ **把 bootstrap 槽刷坏**，每次开机卡 30–40 s 回待机，
  最后靠 U 盘救砖。
- ⟹ 含长空转/长循环的镜像**禁止进 boot 槽**；先在 recovery 槽或纯计算里核对迭代数。

**按电源键之前先确认设备不在 Android 运行态。**

- Android 运行中按电源 = 待机 = PM51 切电 = 硬断电（`/data` 风险）。工具 `tools/host/tvpower.sh` 默认拒绝，需 `--force` 才按。
- 只能用于「待机/挂死 → 开机」这个方向；救砖（按住机身键 + 插电）IR 做不了。

**「设备自己回来了」不能当「狗咬了」的证据。**

- 必须另有一个**不依赖时间**的判据证明这一轮确实进过 recovery：`misc` 第 2 页标记是否被
  `mmc erase.p misc` 擦掉。
- 代价：2026-11-21 把几次「26 s 自己回 Android」当成 `wdt_enable` 生效，据此写下「10 s 狗是
  有效兜底」，后来用标记法才知道那几次**根本没进 recovery**（BCB 没写进去，走了 `bootcmd`），
  而真进了 recovery 的两次都是**挂住不恢复**。

**`boottest.sh arm` 只许执行一次。**

它每次都**无条件**备份"当前槽内容"。arm 两次就会把我们自己的镜像当成厂值备份，
`rec.head.bin` 永久失效，厂值回不来了。

**`precheck` 通过 ≠ 可以 arm —— 它检查的是备份文件，不是槽内容。**

2026-11-20 实际踩过：`precheck` 报 `rec.head.bin md5 = 0f6e1705`（厂值）✓，
同时槽头 `kernel_size = 0x00d3fd60` —— 那是 **rung0 的**（厂值是 `0x012d4a00`）。
两个字段互相矛盾，而我只看了前者，于是第二次 `arm`，把 rung0 备份成了"厂值"。

⟹ **arm 前必须直接对比「槽内容 md5」与「厂值 md5 `0f6e1705…`」**，
不能只看 `rec.head.bin`。槽里有我们自己的镜像时，先决定要不要先恢复厂值再 arm。

⟹ 附带事实：**`rescue-fast.bin` 不恢复 recovery 分区**（2026-11-20 实测：救砖后槽里仍是 rung0）。
它恢复的是 `misc` + `boot`。所以"救过砖"不代表槽是干净的。

⚠️ **上一条要按 md5 区分，别按文件名。** 47,263,776 B 这个尺寸有两个包：

| md5 | 脚本里有 recovery 段 | 用处 |
|---|---|---|
| `7e8ef7a7…`（`fix/rescue-fast.bin`） | **有**（`filepartload 0xA000 0x1A33000` + `erase.p` + `write.p`） | 真能重写 recovery 槽 |
| `326132c7…`（`fix/rescue-norecovery.bin`） | **无**，只有注释行 | 只写 misc/dtb/boot，修不了坏槽 |

2026-11-20 救砖失败的直接原因就是 U 盘根目录放的是后者（名字同样叫 `V8-…bin`）。

**U 盘纪律**

- 根目录**只能有一个 `.bin`**，且文件名必须是 **`V8-T652T03-LF1V147.bin`**。mboot 找包是
  prefix + postfix 拼接（`filenamefind %s .bin`），TCL 配的前缀是 `V8-`；**只放
  `MstarUpgrade.bin` 时它根本不会去读**（2026-11-17 第四次实测，同名双份也成功过）。
- 强制升级要从**关机状态**开始：拔电 → **按住机身实体电源键** → 插电 → 按住 10–15 秒直到
  出现进度条才松手。**不是**"插电进待机再按一下"。
- 救砖包 `rescue-fast.bin` **自己不设** `MstarUpgrade_complete` key ⟹ 每次救砖后要手工重置成 1，
  否则下次插 U 盘会被强制升级。

## 3 观测纪律：不要拿寄存器去试错

**禁止 MMIO 盲扫。** 厂商块里有未实现的空洞，读到就 external abort，arm64 直接 panic。
代价：曾在 `0xFD200000+0..0x40000` 按 `0x100` 步长扫 USB 块，电视当场重启。

**碰新块先用对齐的字宽读**（`readl`），不要逐字节 hexdump。
代价：按字节读 HDMI RX 块（`pm+0x2E7000`），电视再次重启。

**地址算术错一位不会报错**，只会读到"平静的一整片 0"。凡读到全零，**先复核算术**再怀疑硬件。
（`pm+0x22600` 是 `0xffffff800a022600`，不是 `…0a226000`。）

**读之前记 uptime**；崩了第一时间抓 `/sys/fs/pstore/console-ramoops`。
Android 的 init 会在启动时清 pstore，晚几分钟就只剩新启动的日志。

**内核符号地址只能用 `kallsyms_lookup_name` 在模块内取。** `/proc/kallsyms` 全是 0，
`kptr_restrict=2` 对 root 也生效。

**`insmod` 用 `/vendor/bin/busybox`。** toybox 的走 `finit_module(2)`，在这台机器上会自旋。

**提权走 `/data/local/tmp/tvroot.cmd`**：写命令 → 等 12–15 秒 → 读 `tvroot.out`。
调用封装是 `~/Debian/m7642-build/scripts/tvrun.sh <本地脚本>`。

**`adb` 的 server 会随上一个 shell 结束而死**，`connect` 与动作要写在同一个调用里。

**dmesg 必须在 9 秒内抓。** 环缓冲里 0–8.x 秒的 `setup_arch` 段会被 `avc: denied` audit 洪水冲掉。
`loglevel=3` 只约束控制台、**不约束环缓冲**（所以"被 loglevel 挡住了"这个解释是错的）。
采集**不要**用 `adb reboot recovery`：会锁 recovery 循环，且 recovery 里 adb 多半不可用，回不来。

## 4 构建纪律

**7.3 只走 `~/Debian/m7642/tools/build-mstar-kernel.sh`。**

- 裸 `make -j8 Image` 不带 `ARCH` 会进**交互式** `syncconfig`，卡住。

- 梯级（rung）是独立汇编的 ⟹ **改梯级零内核重编**，别为了改一个颜色重编整个内核。

**4.19 树（原 `~/kbuild/tcl-419/`，2026-11-22 已删除）专属**

- `make clean` 是**坏的**（`No rule to make target 'clean'`）⟹ 改用 `tcl419-clean.sh`。
- 厂家把构建产物（`.o`/`.a`/`.cmd`/`modules.order`）**提交进了 git**。只删一部分 `.o` 会让 kbuild
  以为目录归档还在，报 `ar: <dir>/built-in.a: No such file or directory`
  ⟹ **要么全删要么不删**（`*.o *.a .*.cmd .*.o.d *.mod *.mod.c *.ko modules.order modules.builtin
  .tmp_* *.symvers` 一起清）。

- **sandbox 的 `rm` 包装器**在一个 turn 内删到第 50 个文件就拒绝，会杀掉 kbuild 的 `.tmp_*` 清理。
  编译时用 `env -i PATH=<toolchain>:/usr/bin:/bin`——**PATH 里不能有 `safe-bin`**。

**动手之前先查有没有残留后台任务在改这棵树。**
代价：上一次会话残留的 `git checkout -f HEAD` 跑了 3 h 30 m，期间补丁"静默回滚"、
`fixdep` 执行位被重置，整整三小时的失败都源于它。

**★ 上机前从 `autoconf.h` / `System.map` 复算，不要相信文档里的"当前配置"。**

交付代价：2026-11-20 重编的 7.3 Image 实际是 `CONFIG_MSTAR_M7642_BUILTIN_DTB=n`，
而 boot-test §二十五/二十六 的方案依赖 `=y`；mboot 又只交 `x0=0` ⟹ `setup_arch` 拿不到设备树。
此后 11-20→11-22 所有「MMU 之后挂住」的判定都建立在这个镜像上，而且「MMU 已开」还是靠一个
**否定项**（`__no_granule_support` 未到达）推出来的。

⟹ 每次上机前把这三样抄进日志：`grep MSTAR .config`、`grep MSTAR include/generated/autoconf.h`、
`grep -E " (_end|boot_args|primary_entry)" System.map`；镜像 md5 与这三样写在一起。

**★ 检查点镜像必须与"已验证档"保持同一组补丁。**

所有带 stash 验证的深检查点（`0x455048` / `0x465E4C` / `0x465E78`）都是在

2026-11-22 01:0x 的 post-MMU 镜像漏了这个 nop，NO_RETURN 因此**无法归因**（可能是内核没到，
也可能是漏补丁导致的早挂）。

⟹ 新镜像的补丁清单（nop、shim、tramp、handover）写进文档，构建脚本里固定下来，别靠手打。

## 6 文档纪律

- **★ 开工前先查，别凭记忆分析。** 任何"对比 / 排查 / 核对"动手前，先 `grep -l <关键词> *.md`
  扫一遍 `index.md` 的指针表。2026-11-20 就犯过：又去 grep 4.9 的 `head.S` 找 MIU 偏移和
  `NODTB`，而 `confirmed-facts.md` 第 32 行和第 194 行早就有结论（前者在确证事实里，
  后者在"已否定"表里）。**重复劳动不只是浪费——它会让人以为"刚发现的"，进而推翻已有结论。**
- **★ 查关键词要从「问题」出发，不要从「地址 / 变量」出发。** 同一天第二次栽在同一处：
  要判断"DDR 能不能跨重启保留"，却只 grep 了地址 `43300000`，没有 grep
  `跨重启` / `保留` / `ramoops` / `soft reset` —— 而结论（"只在 soft reset 下保留；
  救砖要断电，DDR 全丢"）就在那组词下面。**结论因此被搞反，还写了一整套"否证"。**
  ⟹ 查之前先自问："这个结论如果存在，它会用哪些**概念词**写？"至少用两组词各查一次。
- 每篇文档体例固定：**结论 → 证据 → 对主线的意义 → 待办**。
- 数字必须能在本机复算（给命令，不只给结果）。
- 写"已否定"的假设时要留原假设的文字 ⟹ 防止以后有人重新走一遍。
- 文档与记忆的边界：**记忆只放"决定下一步动作"的事实 + 指针，细节进文档。**

### 关中断的调试窗口要格外小心

`setup_arch` 里有一段 `msr daif,#0xc0` + `msr ttbr0_el1` + `tlbi vmalle1` 的代码
（`0x46395c`–`0x4639b0`）。**中断关着的时候任何异常都不会被打印，只会变成死循环**，
外部表现与"内核挂死"完全一样，而且这类挂在 `0x463958` 之后出现时
`0x463a04` 这类点会"记录为空"——**不能凭"记录为空"断定内核没到过附近**，
还要看是不是分支跳过去了（`0x4639d4`/`0x4639e8` 两条支路都绕过 `0x463a04`）。

### 探针的访存地址必须跟 MMU 状态匹配（血的教训）

MMU **关**时要用物理地址；MMU **开**时物理地址不是"物理地址"，是**用户态 VA**，
要靠 TTBR0 的恒等映射才落到内存。`setup_arch` 里的 `cpu_uninstall_idmap()`（`0x463978`）
会把恒等映射拆掉 ⟹ 之后任何"按 PA 写"的探针都会**取数中止**，而那一刻 IRQ/FIQ 已被
`local_daif_restore` 屏蔽，中止变成死循环，**外部表现与内核挂死无法区分**。

⟹ 判据：如果某一发"记录为空"，先问**探针在那一点能不能合法访存**，再怀疑内核。
这一条之前害我们误判了 5 发（`c1`/`c2`/`b1`/`e0`/`e1`），每发还花掉一次人工拔电。

### 上机前一次只改一处，而且先在最"无害"的点验证

2026-11-22 晚上一次改动同时引入了三个新机制（`AT` 自校准、VA 访存、自建恒等映射），
结果**连续 3 次在本来能回来的检查点上挂死**，每次都要人工拔电，且挂死时读不到记录
（DDR 随断电丢失），**没有任何信息产出**——这是最坏的一类失败。

规则：
1. 新机制先在**已知能回来**的点上单独验证，通过了再叠加下一个；
2. 每次改动都要能回答"如果它挂，我损失什么"——如果答案是"什么都没学到"，
   就必须把改动拆小；
3. 挂死不可自愈（无 WDT、无红外），**每一发都要当作有预算**。

### 测试台要按"真实调用路径"验，不能只按符号验

2026-11-22：QEMU 夹具一直用 `bl _start_kva`（按符号）进入 tramp，而真实镜像是
`bl Image+0x36c004`（按**硬编码偏移**）。一次重写让 `_start_kva` 从偏移 4 漂到 8，
夹具照样全 PASS，真机连挂三发。**偏移量必须由构建生成并断言，夹具必须复现补丁路径本身。**

### 静态分析优先；每次断电都是硬件损耗（2026-11-23，用户要求）

即使用户已经买了智能插座（可脚本化断电），**仍不允许"先打一发看看"**：

1. **打点前必须先用静态分析缩小范围**（反汇编 + 源码 + 符号/结构体布局），
   把候选点压到 1–2 个再上机；
2. **优先设计"会正常返回"的发数**：能在一个"已知会回来"的检查点上读数据，就不要在
   `可能挂死` 的点上试探。为此新增了 readout 入口（见 `confirmed-facts.md` §34.25）；
3. **一张镜像放多个互斥探针**，用记录里的 `x30` 判断走了哪条路——把 4 发压成 1 发；
4. 每次断电重启对电源/存储都是冲击，**发数本身就是预算**。

反例（当天）：`mm5` 之后直接打了 `combo`，虽然信息量高，但那条路本来就有一半概率挂死；
而 readout 这种"必定返回"的仪器应该先做。

### 重启手段的优先顺序（2026-11-24，用户重申）

1. **静态分析**（反汇编 / 源码 / 符号与结构体布局）先缩小到 1–2 个候选点；
2. **优先设计会返回的发数**（readout、计数型返回探针、互斥探针），这类发数**零断电成本**；
3. 红外 `tools/host/tvpower.sh`（把断电→上电当作"待机复位"）只在挂死且不得不断电时用；
4. **最后**才用智能插座 `tools/host/socket.sh cycle`（米家"电视插座"，`zimi.plug.zncz01`）。

**每一轮断电重启对电源与存储都是冲击，发数本身就是预算。**

### 每批必带"对照探针"（2026-11-24 审计后新增）

`❌`（Android 没起来）**不能单独作为判决**。历史上已有三条 ❌ 被追溯为仪器问题
（§34.17 的 PA/VA 写错、§34.29 的 `d3` 结构性假阴性、以及多次设备/插座状态事故）。

⟹ 每批第一发固定打**已知必回**的对照点（当前用 `0x4772b4`，镜像 `ctl`）。
**对照没回来 ⟹ 本批全部作废**，不要据此改内核结论。

### 探针 blob 覆盖的是活代码，不是"填充"（2026-11-24 审计发现）

`tramp-postmmu.bin`（0x778 B）放在 `Image+0x36c000`，System.map 显示该区间有 9 个真实符号：
`queued_spin_lock_slowpath`、`queued_read_lock_slowpath`、`_raw_spin_trylock`、`_raw_read_lock*` 等。
**任何一次锁竞争/慢路径都会跳进 blob 乱跑 = 挂死，与内核真挂死同形。**

⟹ 解释 ❌ 时必须同时考虑这条；将来要么把 blob 挪到真正死掉的代码段（如 head.S 早期代码），
要么把 blob 缩小到能放进一个可证明不执行的函数里。

### 动手前先确认目标设备身份

2026-11-24 因为 `mihome-ctl` 用的是 3 天前的设备缓存，控错了插座（`1043054088` 墙壁插座），
白折腾 4 小时并误判"设备掉线"。
⟹ 涉及外部设备时，先用云端实时列表核对 `did`/`model`/`name`（`tools/host/live_devices.py`），再动手。

### 打点地址三步核实（2026-11-25 新增）

选一个打点地址前，必须确认三件事，缺一条就会白烧一发：

1. **它落在哪个函数里**（`objdump` 看符号边界）——本轮把 `sched_init_smp` 的地址当成
   `sched_init` 的，得出两个无意义的 ❌；
2. **该函数在当前执行路径上**（不在路径上的点必然 ❌，与内核是否挂死无关）；
3. **该地址是正常指令**，不是 `brk #0x800`（`BUG()` 占位）——打到那里等于人为触发 bug。

另外记住：`bl f()` 处的终结型探针会**跳过 `f()`**，所以"到达"只证明调用前一切 OK，
不证明 `f()` 能跑；要验证函数体，必须打到函数内部或它的返回点之后。

### 镜像管道：`--image` 必须是裸内核，容器由工具自己包（2026-11-25 血账）

`tools/host/mk-mainline-abort.py` 的参数语义：

| 参数 | 含义 |
|---|---|
| `--image` | **裸 arm64 Image**（以 `MZ` 开头）——工具会把它和 stub 拼起来并打补丁 |
| `--src`   | **容器模板**（`ANDROID!` 头从这里复制，`kernel_size` 等字段会被重写） |
| `--out`   | 输出容器 |

**不要**在调用前自己把 Image 包成容器：结果是**容器套容器**，mboot 会把外层
`ANDROID!` 头当代码执行，内核在 `head.S` 第一步就死，探针永远打不到任何检查点，
外部表现与"内核挂死"完全同形。2026-11-25 因为这个白花了约 4 小时、几十发断电。

**硬断言（已加进 `probes/handoff/mkimage.sh`）**：`make Image` 之后断言
`Image[:2] == b"MZ"`，否则报错退出。`mkimage.sh` 只做 `make dtbs Image`，不包装。

### 对齐补丁点只能按符号取，不能按字节特征搜（2026-11-25 血账）

2 MB 对齐修正打在 `__pi_early_map_kernel + 0x3c`（`0x92405279` = `and x25,x19,#0x1fffff`
→ `mov x25,xzr`）。**`.pi.text` 在 `System.map` 里没有符号**，所以那段代码会被归到相邻函数；
但我曾改成"在镜像里搜唯一的 `0x92405279`"，结果在 7.3.5 构建里**搜到的是 0x465224**
（别处的巧合同值指令），于是补丁打到了无关代码上、而真正的对齐 bug 从未修 ⟹ 内核死在
`head.S`，探针全部打不到，同样与"内核挂死"同形。

**硬断言（已加进 `probes/handoff/mk-multi.sh`）**：`ALIGN_OFF=$(resolve zfix_align)`
（`ckpt.py` 的符号相对定义），并在打补丁前校验该处的字确实等于 `0x92405279`，不等就退出。

### 每张镜像必须留元数据

`mk-multi.sh` 现在会在镜像旁写 `m7642-<tag>.meta`：镜像/kimage/System.map/config 的 md5、
对齐点、nop 点、`tramp_at`、`save_va`、补丁清单、构建时间。
代价：2026-11-25 曾丢掉 05:24 那个可用内核的**确切配置**（`IKCONFIG` 未开，无法从镜像里抠出来），
导致无法复现，只能靠"重新推导 + 逐项对比"恢复。

### 设备上的 `dd` 不支持 `conv=fsync`

`dd: conv option disabled` ⟹ 写 recovery 槽的脚本**不许带 conv 选项**；写完用 `sync`。
runnner 还必须**校验槽内 md5**（按镜像真实长度、4096 对齐、在设备侧算 md5），
否则会拿旧镜像去开机而毫无察觉。

### 判据复述（本项目多次踩）

- **"到达"必须由 stash 证明**：`magic == "M764"` 且 `x30 == site + 4`。
  "设备回来了"可能是插座恢复/正常开机，不算数。
- **等待预算**：交接链 30–35 s + Android 到 `boot_completed` ~25 s ⟹ **120 s** 足够；
  没起来就用智能插座恢复（`socket.sh recover`）并判 ❌。文档里 300 s 的老规则是
  没有插座时代的产物，已作废。

### 远程调试时，"看屏幕"不是可用通道（2026-11-25）

用户是**在办公室经 WireGuard 连回家里的电视**调测的 ⟹ **没人能看屏幕**。
所以：

- 远程唯一可用的读数只有两条：①**stash 交接**（`magic "M764"` + `x30`）；
  ②**用户态把 dmesg 写进 PA `0x23082000`**（报告页 `0x23081000`），交接后读回。
- `fb0`/fbcon 修好（§34.41）是移植成果本身（`console=tty0` 生效、现场能看日志），
  **但不要拿它当远程判据**，也不要让远程用户"看一眼屏幕"——那是无效请求。
- 想留现场可见的记录，用上面的 PA 页通道；想让人看，只能等人在现场。

### 我们的内核跑起来后，PM51 会在 ~40 s 内把电视切到待机（2026-11-25 实测）

刷"纯启动、不交接"的镜像（内核常驻、`/init` 只 pause），40 s 后插座功率读数从 76–81 W
掉到 **11 W** ⟹ 电视进了待机 ⟹ PM51 自己切的。含义：

- 所有"不交接"的实验都要在几十秒内完成，否则机器会睡；
- 想让内核长期驻留，需要处理 PM51 / 待机路径（vendor 内核里由 PM 驱动喂状态机）；
- 恢复仍然是 `tools/host/socket.sh recover`（OFF → 10 s → ON → 3 s → IR POWER）。

### "挂死"无法被任何内核检测器救回（2026-11-25 实测）

eMMC bring-up 期间试过把"卡住"转成"panic"，好让 panic 探针接手拿日志：

```
CONFIG_DEBUG_KERNEL=y
CONFIG_SOFTLOCKUP_DETECTOR=y   CONFIG_BOOTPARAM_SOFTLOCKUP_PANIC=1
CONFIG_DETECT_HUNG_TASK=y      CONFIG_BOOTPARAM_HUNG_TASK_PANIC=1   (timeout 30)
```

**实测无效**：装了这个内核照样"挂死 + 无 Android + 记录为空"。
原因：那几个检测器都靠**定时器中断**驱动，而这台机器上遇到的挂死多数发生在
**中断被关掉**的路径里（`setup_arch` 的 `msr daif,#0xc0` 窗口、驱动锁内轮询等），
中断不来 ⟹ 检测器永远不跑 ⟹ 没有人 panic。

**结论（再次确认）**：不存在"挂了还能自动回来 + 记录还在"的路径。
⟹ 每一发都要当成有预算：**优先设计会返回的探针**，把可能挂死的动作拆到最小，
并且在动手前用静态分析把候选压到 1–2 个。

（这套配置本身无害，留在 `.config` 里可以兜住"中断正常但任务卡住"的情况。）
